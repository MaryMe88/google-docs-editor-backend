# Решение по auth._soft_auth_warned — 2026-11-15

## Назначение

Документ фиксирует решение **принять `auth._soft_auth_warned` как
допустимый технический долг** без изменения runtime-кода.

**Это фиксация решения, не рефакторинг.** Код `src/auth.py` в этой
итерации не меняется.

Связанная итерация: 16.2 карты №3 «Контракты и сложный рефакторинг».

**Дата решения:** 2026-11-15.
**Следующий пересмотр:** при изменении модели деплоя или требований
к аудиту soft mode (см. раздел «Условия пересмотра»).

## Контекст

Эндпоинты, защищённые `verify_api_key`, работают в двух режимах:

| Режим | Условие | Поведение |
|---|---|---|
| Строгий | `API_SECRET_KEY` задан | Ключ обязателен, сравнение через `secrets.compare_digest` |
| Soft mode | `API_SECRET_KEY` не задан | Запросы пропускаются без аутентификации; в лог пишется **одно** предупреждение за время жизни процесса |

Soft mode — совместимость с деплоями без ключа. Чтобы открытый доступ
не остался незамеченным, `verify_api_key` сигнализирует один раз — не
на каждый запрос. Это то, ради чего существует `_soft_auth_warned`.

## Что принимается как долг

| Поле | Значение |
|---|---|
| Подтверждено | Да |
| Файл | `src/auth.py` |
| Определение | `_soft_auth_warned: bool = False` (строка 20) |
| Чтение/запись | `verify_api_key`: `global` (41), чтение (47), запись (53) |
| Контракт | Одно предупреждение на процесс; не на запрос, не на инстанс приложения |
| Runtime-потребители | Только `src/auth.py` |
| Тестовые потребители | `tests/test_retry_auth_polish.py::test_soft_auth_logs_warning_once`; сброс флага в `tests/test_retry_auth_polish.py:115` и `tests/test_production_auth_hardening.py:112` |

## Почему это допустимо

1. **Не влияет на безопасность.** Флаг управляет только частотой записи
   предупреждения в лог. Контроль доступа реализован отдельно и
   корректно: при заданном ключе — обязательная проверка через
   `secrets.compare_digest`, при отсутствии — пропуск по согласованному
   контракту soft mode.
2. **Ограниченный объём.** Одна переменная, три строки кода, один
   тест-сценарий. Никакие другие модули флаг не используют.
3. **Осознанный контракт.** «Один раз на процесс» — адекватная
   гранулярность для защиты лога от спама. `global` здесь —
   идиоматичный для Python инструмент одноразового предупреждения,
   а не забытое состояние.
4. **Тестовая изоляция есть.** Тесты явно сбрасывают флаг, состояние
   не протекает между сценариями.
5. **Наблюдаемость сохранена.** Предупреждение действительно появляется
   в логе при старте soft mode.

## Рассмотренные альтернативы

| Вариант | Суть | Почему отклонён |
|---|---|---|
| `@lru_cache(maxsize=1)` | Перенести флаг в декоратор приватной функции | Контракт «один раз на процесс» не меняется, состояние переезжает внутрь декоратора. Косметика без содержательного выигрыша; для `bool`-флага нет выигрыша и по потокобезопасности |
| Явное per-instance состояние через `app.state` и DI | Прокидывать состояние через `verify_api_key` и цепочку зависимостей | Меняет сигнатуру зависимости, требует правки роутеров, тестов HTTP и dependency overrides, может затронуть OpenAPI. Главное — **ухудшает контракт**: «один раз на инстанс приложения» вместо «один раз на процесс»; в production инстансов больше, чем процессов — предупреждений станет больше, а не меньше |

## Принятые риски

| Риск | Ожидаемость | Дата пересмотра |
|---|---|---|
| Несколько процессов (`uvicorn --workers N`) — каждый напишет своё предупреждение | Ожидаемо и полезно: видно, что каждый воркер в soft mode | При изменении модели деплоя |
| Рестарт процесса — предупреждение повторится | Ожидаемо и полезно: каждый запуск без ключа виден в логе | При изменении модели деплоя |
| Потокобезопасность записи `bool` | Худший сценарий — два предупреждения при гонке первых вызовов; не критично | — |
| Флаг не сбрасывается при смене `API_SECRET_KEY` в рантайме | Не применимо: `API_SECRET_KEY` читается через `os.environ` при каждом вызове; флаг влияет только на факт «уже предупредили» | — |

## Условия пересмотра

Решение пересматривается, если:

- Появится требование «предупреждение на инстанс приложения»
  (например, мультитенантность) — тогда станет актуален вариант с
  per-instance состоянием.
- Изменится модель деплоя так, что количество процессов перестанет
  быть осмысленной гранулярностью.
- Появится требование к структурированному аудиту soft mode
  (например, отдельный counter в метриках) — тогда флаг заменяется
  на метрику, а не на другой способ логирования.
