\# Rate limiting assessment — 2026-10-10



\## Назначение



Документ фиксирует состояние rate limiting в проекте и решение

о его дальнейшем развитии в рамках итерации 3 новой дорожной

карты остаточных security-работ (issue #35).



\*\*Это результат анализа, а не только кода.\*\* Ключевые факты собраны

из логов production (Render) и исходников; на их основе принято

решение не строить распределённый лимитер сейчас.



\## Что используется



| Параметр | Значение |

|---|---|

| Библиотека | `slowapi==0.1.9` |

| Хранилище | \*\*in-memory\*\* (без Redis) |

| Ключ | `\_client\_ip\_key` → `get\_remote\_address(request)` |

| `X-Forwarded-For` | \*\*игнорируется\*\* (защита от подделки) |

| Лимит `/api/edit` (prod) | `10/minute` |

| Лимит `/api/edit` (тесты) | `1000/minute` |

| Лимит `/health` (prod) | `60/minute` |

| Лимит `/health` (тесты) | `1000/minute` |

| Лимит `/livez` | \*\*нет\*\* (не защищён) |

| `Retry-After` в 429 | \*\*есть\*\* (`headers\_enabled=True`) |

| `X-RateLimit-\*` в ответах | \*\*есть\*\* (`headers\_enabled=True`) |



Исходники: `src/rate\_limit.py`, `src/routers/edit.py`, `src/routers/health.py`.



\## Ключевое наблюдение из логов production



Из логов Render за 2026-10-10:

INFO: 81.28.13.63:0 - "POST /api/edit HTTP/1.1" 200 OK
2026-10-10 10:55:09,228 - src.main - INFO - {"timestamp": ...,
"method": "POST", "path": "/api/edit", "status_code": 200,
"duration_ms": 3557.01, "client_ip": "81.28.13.63"}


**Что это значит:** за reverse proxy Render `request.client.host`
содержит **реальный IP клиента** (`81.28.13.63`), а не адрес прокси.
То есть `get_remote_address` работает корректно, и лимит считается
per-client. **Это ключевой вывод итерации:** распределённый
rate limiter не нужен для корректности.

## Что оказалось неожиданным: `--workers 2` игнорируется

`render.yaml` объявляет:

```yaml
startCommand: uvicorn src.main:app --host 0.0.0.0 --port $PORT --workers 2

Однако в логах Render видно:

==> Setting WEB_CONCURRENCY=1 by default, based on available CPUs in the instance
==> Running 'uvicorn src.main:app --host 0.0.0.0 --port 10000'

Render игнорирует флаг --workers 2 и запускает uvicorn с
WEB_CONCURRENCY=1. Фактически в production один воркер, а не два.

Следствия:

In-memory rate limiter не страдает от рассинхронизации
(проблема «два воркера считают независимо» отсутствует).

Эффективный лимит /api/edit — ровно 10/minute, а не 20/minute.

render.yaml вводит в заблуждение — это известное расхождение
между документацией и реальностью. См. раздел «Остаточные риски».

Что защищено, что нет
Защищено
/api/edit — лимит 10/minute на IP клиента. Если лимит
исчерпан, возвращается 429 с заголовками Retry-After и
X-RateLimit-*.

/health — лимит 60/minute. Даже при утечке API_SECRET_KEY
злоумышленник не сможет бесконечно вызывать /health?deep=true
и жечь токены OpenRouter быстрее этого лимита.

/livez — сознательно без лимита: healthcheck Render
вызывается часто (раз в 5 секунд), и лимит помешал бы.

Не защищено
Распределённые атаки. Если злоумышленник использует ботнет
с разных IP, 10/minute на каждый IP даст много запросов
суммарно. Для этого нужен бы лимит на API-ключ или
глобальный — но у нас один ключ на всё Apps Script-приложение,
так что per-API-key будет эквивалентен глобальному и заблокирует
легитимных пользователей.

Защита от «сжечь баланс за 1 час с одного IP». При 10/minute
один IP может сделать 600 запросов в час. Если каждый запрос
тратит, скажем, 0.005 USD — это 3 USD/час. При среднем
использовании — некритично. Если OpenRouter balance маленький,
см. раздел «Что делать при росте нагрузки».

Решение
Оставляем текущую конфигурацию. Дополнительно:

Включён headers_enabled=True — теперь slowapi отдаёт
Retry-After и X-RateLimit-*. Клиент (Apps Script) может
подождать указанное время перед повтором.

Новый лимит /health (60/minute) — закрывает вектор
«много deep=true запросов жгут токены OpenRouter».

Добавлены тесты — tests/test_rate_limiting.py (10 шт.)
закрепляют конфигурацию и заголовки.

Redis не внедряется. Обоснование:

IP определяется корректно за прокси Render (см. выше);

фактически один воркер (WEB_CONCURRENCY=1);

in-memory лимитер живёт процесс, для нашего масштаба
(десятки запросов в час от одного пользователя) достаточен;

Redis добавил бы внешнюю зависимость, сетевые задержки
и потенциальную точку отказа.

Когда вернуться к этому вопросу
Пересмотреть решение, если произойдёт любое из событий:

Render перейдёт на платный план и начнёт запускать несколько
воркеров (WEB_CONCURRENCY >= 2). Тогда in-memory лимит
перестанет быть точным.

В логах появятся признаки распределённой атаки (много разных
client_ip с одного конца света).

OpenRouter balance начнёт расходоваться быстрее, чем ожидается
от легитимного использования.

Появится второй независимый клиент (не Google Apps Script) —
тогда имеет смысл сделать лимит на API-ключ, а не на IP.

При наступлении любого из этих условий — пересмотреть, нужен ли
Redis-backed limiter или более хитрый ключ.

Известные ограничения
Расхождение render.yaml и реальности
render.yaml объявляет --workers 2, но Render игнорирует флаг
и устанавливает WEB_CONCURRENCY=1. Это не критично для
rate limiting, но:

может ввести в заблуждение при чтении конфига;

если Render когда-нибудь начнёт соблюдать --workers 2 (например,
после смены плана), лимит 10/minute фактически превратится
в 20/minute.

Что делать: вынести правку render.yaml (убрать --workers 2,
полагаться на WEB_CONCURRENCY) в отдельный PR — это изменение
инфраструктуры, а не кода, и его не следует смешивать с security-правками.

In-memory storage
Limiter(key_func=..., headers_enabled=True) без storage_uri
использует in-memory хранилище. Это значит:

лимиты не переживают перезапуск приложения;

лимиты не синхронизируются между процессами (сейчас это
не проблема — один воркер, см. выше).

Для нашего масштаба это приемлемо.

Что не делаем
Не переписываем rate limiter с нуля.

Не внедряем Redis.

Не добавляем лимит на API-ключ (один ключ на всё приложение —
это привело бы к блокировке всех пользователей одним).

Не трогаем render.yaml в этой итерации.
